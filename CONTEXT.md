# Domain model — vaulted-agent-launcher

Single-context glossary for agents and architecture work. Prefer these terms over synonyms.

## Core concepts

| Term | Meaning |
|------|---------|
| **Launcher** | The `vaulted-agent` / `va` binary. Resolves secrets, scrubs the environment, and execs an agent. Not a long-running daemon. |
| **Harness** | A named launch profile (`harnesses.d/<name>.conf`): backend, manifest, command, optional workdir/bin/labels/keep/**alias**. A **day-one Harness** is one with `backend = plainfile` and `manifest = empty.env` as the Inventory reads them: the only shape Harness discovery writes without a vault, and the only one Vault wiring rewires. |
| **Bash harness** | A Harness whose `command` is `bash`. Extra argv is appended (`va bash ./script.sh`). Not `va run` (any program) and not a retired `*-orchestrator` shell wrapper. |
| **Alias** | Per-harness child-env rename after inject: `alias = TARGET = SOURCE` copies the resolved source secret onto TARGET (fail closed if source missing). |
| **Env-blind agent** | Tool listed in `etc/env-blind-agents` that does not consume vault-injected process-env credentials for the usual provider path. Doctor warns; Vault wiring leaves it on `empty.env`, matched by command basename or Harness name. (kimi is **not** in this list — issue #70.) |
| **Conf file** | The `key = value` text format of `defaults.conf` and Harness confs: one line rule (blank and `#` lines are not entries; the key is the text before the first `=`), read and edited through one module (`src/conf_file.rs`). An edit changes only the key it names and writes the file through **File replace**. Distinct from a Manifest, which is dotenv and read through Manifest entry. |
| **File replace** | How the Launcher rewrites a file it owns the whole content of (Conf file, Refs file, Manager-token file, new Harness conf or starter Manifest), through one module (`src/file_replace.rs`). Whole or not at all, through a temp file beside it, following a symlink to its target, and keeping the replaced file's owner and mode unless the caller sets them exactly (a Manager-token file is always 0640; when root writes it, its group is the Service user's, or with no Service user the primary group of `SUDO_USER` when that names a real, non-root account; otherwise it gets the writer's group). Identical bytes are never rewritten. Not the `update` binary install. |
| **Manifest** | The file a harness points at: either **refs** (references only) or dotenv-style secret material (plainfile/sops decrypt). |
| **Manifest entry** | One `KEY=value` mapping as the shared Manifest parser reads it. It may span several physical lines (a double-quoted value, or a bare PEM / JSON key continued below its first line). Quotes are removed from its value. It is the unit that the Manifest check, resolve and `refresh` all agree on (`src/manifest_entry.rs`). |
| **Manifest check** | What the launch gate, `secrets validate` and `edit-manifest` judge a Manifest by: every problem in it, each with its line and whether it blocks the launch, checked against the Backends that read it. The gate fails on the first blocking problem; the editor shows them all (`src/validate.rs`). |
| **Extra manifest** | A Manifest something on the machine reads that no Harness launches from (systemd units, deploy scripts). Recorded in `defaults.conf` as `extra_manifest = <path>[ = <backend>]`; validated with the harness manifests and launchable by nothing (ADR-0006). |
| **Harness discovery** | What adds a Harness conf for each auto-harness agent found for the launch account and lacking an entry: a pure plan (added, kept, found only for the invoking account, not found), applied through File replace. A new Harness reuses the shared binding when every existing Harness agrees, else `plainfile` + `empty.env`, and an Env-blind agent always starts on `empty.env`. Shared by `update --sync-harnesses` and `install.sh`, which keeps no detection of its own (`src/harness_sync.rs`). |
| **Inventory** | Every Harness and Extra manifest a machine's config declares, each with its effective Backend and resolved Manifest path, or the error that stopped it loading. The one walk that `secrets validate` (the no-target and single-target forms alike), `secrets which`, `refresh` (and `setup bitwarden`, through the Refs-file choice), Vault wiring, the Setup interview's Workdir answer, `edit-manifest`, `pick` and Harness discovery share; launch reads a single Harness and does not use it, and the doctor keeps its own Harness loop for now (#74) (`src/inventory.rs`). |
| **Vault wiring** | What makes a machine use a Backend after `setup <backend>`: `default_backend` recorded, the starter Refs file created when absent (0644, no reference shape in its header), and every day-one Harness that is not an Env-blind agent pointed at that Backend and Refs file, with `workdir = caller` added where it has none. The Refs file is the one the Harnesses on that Backend already use, else the Backend's fallback (`openai.env.refs`, `onepassword.refs`, `pass.refs`), which `refresh` shares. `sops` records `default_backend` only. A pure plan built from the Inventory (each Harness wired, or left with its reason), then applied through Conf file and File replace. Runs before Token capture, so it needs no token; `setup <backend> --wire-only` stops there (`src/vault_wiring.rs`). |
| **Backend** | Where secret values come from: `bitwarden`, `onepassword`, `pass`, `sops`, `plainfile`. Typed in the runtime; unknown names fail closed. |
| **Refs file** | Manifest of `VAR=reference` lines — Bitwarden (uuid / name: / project:), 1Password (`op://vault/item[/section]/field`) or pass (a store path). **No secret values** on disk. |
| **Dangling ref** | A refs-file mapping whose reference matches no secret the manager token can see — on 1Password, a missing item or a missing field: the **1Password listing** lookup's absent. Fails the launch closed; `secrets validate` detects one, `refresh` prunes it. Distinct from a malformed ref, which is a shape problem `validate` owns (on Bitwarden, the **Bitwarden listing** parse says why a reference is malformed). On Bitwarden, the launch reports one as the no-match case of a **Resolve failure**. |
| **Resolve failure** | What a Backend reports when a Manifest will not resolve: the Manifest, the Backend's own message, and the Manifest entries it implicates (variable and reference). Built where the Backend learns of the failure. The launch and `secrets validate` render it; neither reads the Manifest again to blame it (`src/backend.rs`). |
| **Bitwarden listing** | The secrets one manager token can see, as one `bws secret list` returns them (id, key, project). The world the launch and `refresh` both judge a Bitwarden reference against, through one lookup: found, absent, ambiguous, or not a reference. The same module owns the Bitwarden refs-line grammar: the four reference forms and why one is malformed, the annotation that carries a **Source recording**, the generated `name:` line and glued-line recovery (`src/bitwarden.rs`). |
| **1Password listing** | The items one manager token can see, as one `op item list` returns them, plus the fields of the items this `refresh` run expanded. The world `refresh` judges an `op://` reference against, through one lookup: found, absent, unexpanded, or not a reference (`src/onepassword.rs`). |
| **Ambiguous ref** | A Bitwarden mapping whose reference matches more than one listed secret (a `name:` key in two projects, or a key twice in one project). Fatal to the launch, never pruned (the secrets exist) and never repaired (which one is meant is the operator's choice). Fixed by qualifying it with `project:` or `uuid:`. |
| **Unchecked ref** | A 1Password mapping into an item this `refresh` run never expanded (not selected, or a read that failed): the **1Password listing** lookup's unexpanded. Nothing was learned about it: reported, never pruned (ADR-0005). |
| **Prune** | `refresh` removing dangling refs from a manifest. Only ever removes what does not resolve — never rewrites or reorders a working mapping — and only under `--prune` or an interactive confirmation. Since ADR-0004 the `--prune` **flag** also gates repairing a renamed ref; prune itself still means removal alone. A recorded `# exclude:` pattern does **not** make a resolving mapping prunable (ADR-0005). |
| **Source recording** | Trailing `# uuid:UUID` on a refs line, naming the secret the line was generated from. Written by `setup` and `refresh` on the lines they generate. Metadata: stripped before the reference is resolved, so it never disambiguates one. Bitwarden only; never backfilled onto lines already on disk (ADR-0004). Spelled and read by the **Bitwarden listing** module (`src/bitwarden.rs`). |
| **Renamed ref** | A refs mapping whose reference matches nothing but whose source recording names a secret still visible under a different key. Repaired in place — reference rewritten, **variable name kept** — not pruned. Distinct from a dangling ref, where the secret is genuinely gone. |
| **Refresh report** | What one `refresh` run — or `setup bitwarden`, which writes its Refs file through the same flow — found in the lines already in a Refs file: every line that does not simply resolve, each listed once: under its fate (renamed, dangling, ambiguous, unchecked, or unjudged — a shape refresh cannot judge), or, if it resolves but matches a recorded `# exclude:`, as mapped-but-excluded. Holds the alias warnings and the edits the run would make (repairs before removals). Built before anything is decided and printed on every run, whether or not the file changes; the `--prune` / confirmation gate then decides about the edits. Refresh's selection and that confirmation are asked through the same line-reading seam as the **Setup interview**, so the gate can be tested without a terminal. `setup bitwarden` never applies them, whatever the TTY state, and points at `refresh --prune` instead (ADR-0003) (`src/refresh.rs`). |
| **Pre-flight report** | What one `secrets validate` run found: every validate target (each Harness and Extra manifest, or the one named) with its verdict, built before anything prints. The Manager token is obtained at most once per kind, and a Manifest several Harnesses share is resolved once. The gate fails when any row fails (invariant 5) (`src/preflight.rs`). |
| **Manager token** | Vault *manager* credential (`BWS_ACCESS_TOKEN`, `OP_SERVICE_ACCOUNT_TOKEN`). Used only to resolve secrets; must never appear in the child agent env. |
| **Manager-token file** | The file `auth_mode = file` reads a Manager token from (`bws.env`, `op.env`). Judged by one probe for the launch, Token capture and `doctor`: it holds a token, holds no value for the key (an empty value included), is missing, is malformed (a line does not parse; the file and line are named) or is unreadable. Holding no value is missing to everyone but `doctor`; malformed and unreadable are faults (invariant 6). Written only by Token capture, through File replace (`src/token_file.rs`). |
| **Secret value** | A resolved secret destined for the child environment. Redacted on Display/Debug. |
| **Agent-owned credential** | Authentication state created, stored, and consumed by the launched agent itself. Outside launcher manifest resolution and rotation; distinct from a Manager token or an injected Secret value. |
| **Machine defaults** | What `defaults.conf` says, read once: auth mode, default Backend, Service user, whether `run` is allowed, and every Extra manifest line, with each key's env override settled in one place. A file that exists but cannot be read, or a value it does not recognise, is an error with its line, never a fallback (`src/defaults.rs`). |
| **Auth mode** | How the manager token is obtained: `file` (token file on disk) or `prompt` (TTY each launch). The configured value comes from Machine defaults; it is one input to the Token source, which settles token loading for each invocation. |
| **Token source** | How one invocation obtains a Manager token (manager-token env var, else prompt when forced or auth mode is `prompt`, else the token file, else a one-shot TTY prompt), settled once from the environment, the `-p` flag and the configured Auth mode. The launch path and other commands load through it; `setup` does not: it obtains its token through Token capture, which is `setup`-only and the only writer of the file. |
| **Setup interview** | The questions interactive `setup` asks: Auth mode, Service user, Workdir and, when no backend is named or picked from Token capture's doors, Backend. Asked only after the command line is checked (an unknown backend, `pass`/`sops` under `--set-token`, a `--wire-only` misuse fail before any question), through one line-reading seam, and answered as data: nothing is written until every answer is in, so a bad backend reply writes nothing, while an empty one skips only the vault. Then applied in order: Machine defaults (`auth_mode`, `service_user`), the Workdir on each Harness the Inventory loads (one that will not load is listed and left alone), Vault wiring, Token capture. `--wire-only` asks nothing; bare `auth-mode` asks its one question through it (`src/setup_interview.rs`). |
| **Token capture** | `setup`-only path that obtains a manager token through one of four doors: a TTY paste, piped stdin under `--set-token`, an exported manager-token env var or an existing token file; verifies every one against the backend; then writes the token file only under `auth_mode = file`. A rejected exported or on-disk token fails `setup` with nothing written. `setup` with no backend named picks one from the same doors: a Backend has one when its env var is exported and non-empty, or its token file holds the key, is malformed or cannot be read (Bitwarden before 1Password), so a faulty file reaches its message rather than another vault. Distinct from load: never runs on the launch path, and never fires for an unreadable existing token file (invariant 6). A malformed one is replaced only through `--set-token`, once the new token verifies; every other door fails with the malformed message. |
| **Operator identity** | The human on whose behalf a Harness is launched; determines personal agent state and source-control attribution. Distinct from the Service user that executes the process. |
| **Service user** | Optional dedicated OS account; launcher re-execs via `sudo -u` so the agent runs as that user. |
| **Conductor link** | Symlink `*-conductor` → fixed harness name; `-H` must not override (narrow entitlement). |
| **Launch path** | scrub → resolve (loading the manager token through the Token source) → drop manager token → exec (story #44: keep small and auditable). |
| **Launch plan** | Pure result of the launch path before handoff: program, agent argv, workdir, child env. Built purely from the Harness, the resolved Secret values and the launch facts (settled Workdir, launch account home, parent-env snapshot, extra argv) (`src/launch_plan.rs`). A thin launch adapter does the resolve, the manager-token drop and the Workdir preflight before it (`src/launch.rs`). Tests assert the plan without process exec. |
| **Launch facts** | What the launch adapter gathers before the Launch plan is built: the settled Workdir, the launch account's home, a parent-env snapshot and the agent's extra argv. The token source and handoff mode stay with the adapter. |
| **Uninstall plan** | What one `uninstall` run would remove, leave alone ("not ours") and keep: the Manager-token files and the age key (`op.env`, `bws.env`, `age.key`, from `Paths`) always, and config unless `--purge`. A symlink is ours only when its canonical target is the launcher. Built purely from what is on disk, then applied by a thin adapter; the Launcher's `uninstall` and `install.sh --uninstall` both use it (`src/uninstall.rs`). |
| **Child environment** | Explicit allowlist construction (`build_child_env`) from a snapshot of the parent environment (UTF-8 pairs only): passthrough + keep + injected secrets (after aliases), then harness `env=` non-secret pairs and optional `bin`→PATH. |
| **Invocation route** | What one command line asks the Launcher to do (a Harness launch, a Conductor link launch, or a management verb) and which Service-user re-exec it takes, decided once and purely before anything runs. The reserved verbs are one typed set; a Harness conf of the same name shadows a verb. The binary's entry point is its only adapter (`src/route.rs`). |
| **Service-user re-exec** | When `service_user` differs from the caller, plan a sudo hop (original argv preserved for sudoers); pure decision, thin adapter. |
| **Caller cwd** | Invocation directory preserved across sudo re-exec (`VAULTED_AGENT_CALLER_CWD`) for `workdir = caller`. |
| **Workdir** | Where a Harness's agent starts: the Caller cwd when `workdir` is `caller`, empty or unset, otherwise a fixed path with a leading `$HOME` / `${HOME}` expanded. The launch preflight and `doctor` judge whether the launching account can enter it through one module, which also owns the traverse-only `setfacl` remedy that `setup` prints (`src/workdir.rs`). |
| **Manifest override** | Launcher flag `-m` / `--manifest` before the harness name: this launch uses another refs file (replace, no merge). Refused under conductor links. |
| **Default section label** | 1Password’s unnamed custom-field section (`add more`); must not appear in generated env **names** (still may appear inside `op://` for inject). |

## Operator surface (acceptance seam)

The **CLI** is the primary and sole public acceptance seam (story #50). Library modules support the binary; they are not a second product API.

Management verbs: `setup`, `refresh`, `secrets`, `doctor`, `auth-mode`, `run`, `edit-manifest`, `pick`, `uninstall`, `update`, `version`, `help`.

Agent-facing ops contract (commands, recipes, failure modes): **`AGENTS.md`**.

## Invariants (do not break casually)

1. Manager tokens never reach the child environment.
2. No secret material on the agent argv.
3. Sudo re-exec replays **original** argv so sudoers matches what the operator typed. The one exception is `pick`: it hops after the menu and replays as though the operator had typed the chosen Harness (launcher flags as typed, then the Harness name, then the rest), so a sudoers grant for `pick` never authorizes more than the Harness picked.
4. Fail closed on unknown backend, bad var names, placeholder refs, and an unreadable or invalid `defaults.conf` (misconfiguration).
5. `secrets validate` is the pre-flight gate before privileged/paid launches — must not fail open. It covers every manifest the machine reads, harness or **extra** (ADR-0006).
6. Unreadable or malformed manager-token files are not reported as missing and do not fall through to an interactive SA-token paste.
7. Conductor invocation must not honor `-H` or `-m` (fixed entitlement).
